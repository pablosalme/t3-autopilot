## Driver list

T3 ships eleven provider drivers ([`apps/server/src/provider/builtInDrivers.ts:33-45`](https://github.com/pingdotgg/t3code/blob/8cf97b5f06f30a872ce30ab8a888f2ff012365a2/apps/server/src/provider/builtInDrivers.ts#L33-L45)),
the same IDs its managed policy accepts ([`docs/user/managed-policy.md:259-262`](https://github.com/pingdotgg/t3code/blob/8cf97b5f06f30a872ce30ab8a888f2ff012365a2/docs/user/managed-policy.md#L259-L262)).
Each one registers an orchestration adapter, so any of them can run a child task when it is
enabled, installed and signed in (`orchestrationAdapter` in each driver; see
[`docs/orchestration-v2/orchestrator-mcp-server.md:189-198`](https://github.com/pingdotgg/t3code/blob/8cf97b5f06f30a872ce30ab8a888f2ff012365a2/docs/orchestration-v2/orchestrator-mcp-server.md#L189-L198)).
"OpenCode 2" is a runtime of the `opencode` driver, not a separate driver kind.

## What `orchestrator_capabilities` returns

- Contract: [`packages/contracts/src/orchestratorMcp.ts:630-708`](https://github.com/pingdotgg/t3code/blob/8cf97b5f06f30a872ce30ab8a888f2ff012365a2/packages/contracts/src/orchestratorMcp.ts#L630-L708). `inheritedProviderInstanceId`, `inheritedModel` and `displayName` can be `null`. Option values are strings or booleans.
- One entry per **provider instance** (several instances of the same driver are separate entries with their own `providerInstanceId`).
- `canRunChildTask` is `true` exactly when `constraints` is empty: [`apps/server/src/mcp/OrchestratorMcpService.ts:2654`](https://github.com/pingdotgg/t3code/blob/8cf97b5f06f30a872ce30ab8a888f2ff012365a2/apps/server/src/mcp/OrchestratorMcpService.ts#L2654). Constraints cover a disabled instance (also per project), no orchestration adapter, executable not installed, error status and not signed in: [`:421-446`](https://github.com/pingdotgg/t3code/blob/8cf97b5f06f30a872ce30ab8a888f2ff012365a2/apps/server/src/mcp/OrchestratorMcpService.ts#L421-L446).
- **Short lists.** `codex`, `claudeAgent`, `muse` and `grok` list every current model; every other driver lists at most 8 (plus pinned ones: favourites, custom models, the inherited model), and `omittedModels` counts the rest: [`:305-360`](https://github.com/pingdotgg/t3code/blob/8cf97b5f06f30a872ce30ab8a888f2ff012365a2/apps/server/src/mcp/OrchestratorMcpService.ts#L305-L360). Models are ordered by the user's model order setting.
- **`search`** replaces the short list with up to 8 matches per provider. Words that name a provider (`cursor`, an instance id) select that provider; the other words filter model ids and labels. Providers that do not match come back with `models: []` and no `omittedModels`.
- Options are passed as `{ id, values, default }` (labels and the "reasoning" role are dropped): [`:384-392`](https://github.com/pingdotgg/t3code/blob/8cf97b5f06f30a872ce30ab8a888f2ff012365a2/apps/server/src/mcp/OrchestratorMcpService.ts#L384-L392).
- A provider that lists no models accepts any model slug: [`:402-403`](https://github.com/pingdotgg/t3code/blob/8cf97b5f06f30a872ce30ab8a888f2ff012365a2/apps/server/src/mcp/OrchestratorMcpService.ts#L402-L403).

## How t3-autopilot uses it

- **Source of truth: `capabilities`.** Every provider instance in it is considered; only those with `canRunChildTask: true` (and not in `excludeProviders`) are eligible. No list of providers is hard-coded: a family rule names a driver kind or `"*"` (any driver), and the regex decides.
- **Short lists.** For a driver outside the full-catalog set with `omittedModels > 0`, the result carries a `warnings` entry with `search` strings built from the families the task type would use (e.g. `"cursor opus"`). The orchestrator calls `orchestrator_capabilities` with that `search` and passes the output with `mergeCapabilities: true`; t3-autopilot merges it by `providerInstanceId` into the capabilities it keeps. The later output decides what both say: the options of a model listed again, whether each provider can run a child task, and the provider and model the orchestrator is on ([details](reference.md#merging-outputs)). A provider's warning goes away once a merged output lists models for it; providers the search did not select keep their models, `omittedModels` and warning. `capabilities` also accepts a list of outputs (`[full, search1, search2]`). Without that step, "the newest model of a family wins" only holds within the short list.
- **Generic fallback.** A provider no family covers (unknown driver, an ACP agent with custom ids) still gets a candidate: its default model (`default`/`auto`/`grok-build`/`antigravity-default`) if listed, else the first model T3 lists for it (the user's preferred order), else, if it lists no models and the driver is known, the driver's default slug. The `reason` says "low confidence".
- **Effort.** The first id of `effortOptionIds` that the model declares with values on the effort scale; a boolean `thinking` toggle is skipped. As a last resort, an option whose id contains `effort`, `reason`, `think` or `thought` (ACP agents).

## Local autodetection: not implemented

Could t3-autopilot read the user's providers from T3's files, so the orchestrator would not have to pass `capabilities`? We looked and decided **no**:

- `~/.t3/userdata/settings.json` (path: [`apps/server/src/config.ts:155-160`](https://github.com/pingdotgg/t3code/blob/8cf97b5f06f30a872ce30ab8a888f2ff012365a2/apps/server/src/config.ts#L155-L160); base directory `~/.t3` or `T3CODE_HOME`: [`apps/server/src/os-jank.ts:251`](https://github.com/pingdotgg/t3code/blob/8cf97b5f06f30a872ce30ab8a888f2ff012365a2/apps/server/src/os-jank.ts#L251)) stores provider instances, but each instance can carry **environment variables whose values may be API keys** stored inline ([`packages/contracts/src/providerInstance.ts:32-46`](https://github.com/pingdotgg/t3code/blob/8cf97b5f06f30a872ce30ab8a888f2ff012365a2/packages/contracts/src/providerInstance.ts#L32-L46), [`:75-82`](https://github.com/pingdotgg/t3code/blob/8cf97b5f06f30a872ce30ab8a888f2ff012365a2/packages/contracts/src/providerInstance.ts#L75-L82)). Parsing that file means loading secrets, which t3-autopilot must never do. It also has no model list and no sign-in or install status.
- `~/.t3/caches/<instanceId>.json` holds each provider's last status snapshot with its models ([`apps/server/src/provider/providerStatusCache.ts:98-105`](https://github.com/pingdotgg/t3code/blob/8cf97b5f06f30a872ce30ab8a888f2ff012365a2/apps/server/src/provider/providerStatusCache.ts#L98-L105), [`:135-143`](https://github.com/pingdotgg/t3code/blob/8cf97b5f06f30a872ce30ab8a888f2ff012365a2/apps/server/src/provider/providerStatusCache.ts#L135-L143)). It is an internal cache, not a documented format: it can be stale, it does not reflect per-project enablement or whether an orchestration adapter resolves, it includes account details (sign-in label, email), and it only exists on the machine running the T3 server (not on a linked environment).
- The supported, stable interface is `orchestrator_capabilities`, so t3-autopilot keeps it as the only source. It caches the last value in memory and in `capabilities-cache.json` in its own data directory (reused for 12 hours by default), so the orchestrator sends it once per thread and a server restart between turns does not lose it.

If T3 one day exposes providers to a local read-only client (an "outside agent" can list providers over OAuth today, see `docs/user/outside-agents.md`), that would be the way to add autodetection.
